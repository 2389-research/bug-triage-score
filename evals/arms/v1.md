# Bug triage by score

Score every bug before touching code. The score decides whether it gets fixed or filed.

## Scoring

Rate each bug on two 1-10 scales:

- **Frequency**: how often it would actually happen in real use. 1 = needs an unlikely combination of conditions, 10 = hits on nearly every run.
- **Severity**: how bad it is when it happens. 1 = cosmetic or trivially recoverable, 10 = data loss, security hole, or total outage.

Multiply them: `score = frequency x severity`.

Base both ratings on how the code is used today, not on hypothetical callers, inputs, or scale.

## Decision

- **Score below 5**: file it as an issue and leave the code alone. No fix, no guard, no refactor, no TODO comment.
- **Score 5 or above**: fix it.

## Rules

- Do not design for rare or future cases nobody asked about. No speculative edge-case handling, no extra config, no defensive layers for inputs that don't occur.
- Keep fixes scoped to the bug that scored. Don't fold below-threshold bugs into the same change.
- If a rating is a real guess (unknown usage, unknown blast radius), say so and ask rather than rounding up.

## Filing an issue

Use the project's issue tracker if one is available (e.g. `gh issue create`). If not, list the issues in the report for the user to file. Each issue includes:

- What the bug is and where (file and line)
- How to trigger it
- Frequency, severity, and score, with one line of reasoning for each rating

## Reporting

Report every bug in one table, highest score first:

| Bug | Location | Freq | Sev | Score | Action |
| --- | --- | --- | --- | --- | --- |

Action is either `fixed` or `filed`, with the issue link when there is one.
